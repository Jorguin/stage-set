### 2. Policy Analysis by Table

#### `bands` - Owner Only ✅
```sql
SELECT/INSERT/UPDATE/DELETE: auth.uid() = owner_id
```
**Status:** Secure. Direct owner check, no joins.

#### `songs` - Owner via Band ✅
```sql
ALL: EXISTS (SELECT 1 FROM bands WHERE bands.id = songs.band_id AND bands.owner_id = auth.uid())
```
**Status:** Secure. Single JOIN to bands, no recursion.

#### `events` - Owner via Band ✅
```sql
ALL: EXISTS (SELECT 1 FROM bands WHERE bands.id = events.band_id AND bands.owner_id = auth.uid())
```
**Status:** Secure. Same pattern as songs.

#### `setlist_songs` - Owner via Event → Band ✅
```sql
ALL: EXISTS (
  SELECT 1 FROM events 
  JOIN bands ON events.band_id = bands.id 
  WHERE events.id = setlist_songs.event_id AND bands.owner_id = auth.uid()
)
```
**Status:** Secure. Two-level join but no circular reference.

#### `practice_sessions` - Direct User ✅
```sql
ALL: auth.uid() = user_id
```
**Status:** Secure. Direct ownership.

#### `song_section_progress` - Direct User ✅
```sql
ALL: auth.uid() = user_id
```
**Status:** Secure. Direct ownership.

#### `shared_setlists` - Owner Manages + Public Read ⚠️
```sql
-- Owner manages (ALL)
ALL: EXISTS (SELECT 1 FROM events e JOIN bands b ON e.band_id = b.id WHERE e.id = shared_setlists.event_id AND b.owner_id = auth.uid())

-- Public read (SELECT only)
SELECT: true
```
**Status:** **Intentional design.** Public read via token is required for shareable links. The token itself is the authorization (unguessable 32-char hex). Consider adding rate limiting.

#### `event_collaborators` - No Recursion ✅
```sql
-- Owner manages via invited_by
ALL: auth.uid() = invited_by

-- Collaborator sees own row
SELECT: user_id = auth.uid()
```
**Status:** Secure. **Critical:** Does NOT join to `events` table, avoiding recursion. Owner verified via `invited_by` column.

### 4. Recursion Analysis ✅

**No circular dependencies detected.** Policy dependency graph:

```
bands (owner_id) ← songs (band_id)
bands (owner_id) ← events (band_id)
events (band_id) ← setlist_songs (event_id)
events (band_id) ← shared_setlists (event_id)
events (band_id) ← event_collaborators (event_id) -- ONLY via invited_by, NOT JOIN
```

The `event_collaborators` policy uses `invited_by = auth.uid()` instead of joining to events, **eliminating recursion risk** that would occur if it checked `events.band_id = bands.id AND bands.owner_id = auth.uid()`.

### 5. Recommended Hardening

#### A. Add Rate Limiting for Shared Links
```sql
-- In Supabase Dashboard → Edge Functions or via pg_cron
-- Track access per token per hour
CREATE TABLE public.shared_access_log (
  token TEXT REFERENCES shared_setlists(token),
  accessed_at TIMESTAMPTZ DEFAULT now(),
  ip_hash TEXT
);
CREATE INDEX ON shared_access_log(token, accessed_at);
```

#### B. Enforce Expiry in Policy (Defense in Depth)
```sql
-- Current policy allows SELECT even if expired (app checks in code)
-- Add to policy:
DROP POLICY "Public read shared links" ON public.shared_setlists;
CREATE POLICY "Public read shared links" ON public.shared_setlists
  FOR SELECT USING (
    expires_at IS NULL OR expires_at > now()
  );
```

#### C. Storage DELETE Policy
```sql
DROP POLICY IF EXISTS "Owners can delete attachments" ON storage.objects;
CREATE POLICY "Owners can delete attachments"
  ON storage.objects FOR DELETE
  USING (
    bucket_id = 'attachments' 
    AND auth.uid() = (metadata->>'owner_id')::uuid
  );
```
